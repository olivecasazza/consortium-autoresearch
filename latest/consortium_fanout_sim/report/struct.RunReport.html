Expand description

One simulated run, in the CON-20 report schema.

Fields§

§schema_version: u32§run: RunMeta§fan_out_depth: u32

Deepest node in the cascade tree, counting the seed as 0.

This is the fan-out width the strategy actually achieved — a log2-fanout over 1024 hosts reports 10.

§fan_out_width: u32

Nodes per level of the deepest round, i.e. the widest ring.

§rounds: u32§time_to_converge: Option<Duration>

Cumulative wall-time until the last node held the closure. None if the run failed before full convergence.

§convergence: Vec<NodeConvergence>

Per-host convergence, sorted by node id.

§edge_throughput: Vec<EdgeThroughput>

Every successful edge, sorted by (src, tgt).

§failure_subtree: Option<FailureSubtree>

None when the run fully succeeded.

§phase_timings: Vec<PhaseTiming>

Deploy-DAG phase timings; empty for a cascade-only run.

§deploy_wall_time: Option<Duration>

Makespan of the simulated deploy, when phase timings are present.

pub fn from_cascade( run: RunMeta, result: &CascadeResult, trace: &CascadeTrace, closure_bytes: u64, ) -> Self

Derive every cascade-side metric from a completed run.

trace supplies the per-edge outcomes and the parent chain; closure_bytes prices each edge. Pass the same seed/closure you gave the executor or the throughput numbers will be fiction.

Source

pub fn with_dag(self, dag: &DagSimReport) -> Self

Attach deploy-DAG phase timings from a DagSimReport.

A cascade-only run leaves these empty; a run that drove both the cascade and the deploy DAG fills all five phases.

pub fn to_json(&self) -> String

Serialize to the CON-20 per-run JSON schema.

Deterministic: node-keyed collections are emitted in node-id order, so repeated runs of the same seed are byte-identical and diff cleanly against a stored baseline.
